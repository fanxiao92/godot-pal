# 测试异常处理规则

本页是当前异常处理入口；历史症状、原始退出、时间线、授权范围和旧结论见[历史诊断记录](../archive/m3/test-diagnostics-history.md)。历史记录不是忽略新失败的清单，当前任务必须按实时 Issue、实际提交、脚本和原始证据重新判定。

## 处理顺序

1. 运行前按[测试职责矩阵](../testing/test-layers.md)选择层，核对当前分支/HEAD、脚本、runsettings、工具链配置和自有证据目录。实际 Godot/GdUnit/Prepare/solution 执行全局串行；未知进程只取 PID/Name，确认归属前暂停。
2. 保留原始命令、cwd、提交/候选身份、数字退出码、stdout/stderr 原字节、TRX、Summary/RunInfo、完整性和必要的自有进程/资源快照。报告工具或外层代理退出不能覆盖测试进程的原结果。
3. 分类而非猜因：功能断言失败、活性问题、会话中止/崩溃、未知退出、输出不完整、资源/Prepare 失败、采证失败分别记录。部分 Passed、`aborted=0`、单条 PASS 或报告 exit0 都不能表示完整通过。
4. 已观察到目标更新但状态错误，按功能失败处理；期限内未观察到必要更新，按未完成/活性问题处理。不得用外部墙钟、协程恢复或后续状态把两类合并。
5. 中止、崩溃、未知退出、损坏/缺失结果或未指定失败立即保留现场并停止。禁止自动重试、续跑、拼接旧 TRX、提高时限、放宽断言、停用捕获或升级工具链来取得通过；新的运行必须有明确授权。

## 时序与变异触发

当任务改动时序、Game 迁移、调度偶发、输出捕获或断言时：Core 通过公开构造/输入/显式时间验证 deadline 前、截止时、晚到不补步、回绕和重新调度；Game 通过真实输入交付及已核实的 `UpdateCompleted` 等生产完成边界验证引擎接线。二者证据互补，集成等待不能替代 Core 精确时间，Core 通过也不能证明信号/资源/场景连接。

保留有界等待作为防挂起保护，并把同一单调时钟与帧身份只记录在必要的输入交付、更新进入/完成和状态观测边界。变异逐例运行、逐例恢复；核源码及实际运行目录的 DLL/PDB，必要时显式 Rebuild。只有指定功能断言失败才算捕获目标错误；编译失败、缺资源、崩溃或超时不算反例通过。

## 工具链与历史症状

工具链版本、固定包消费和 bootstrap 以[当前包消费说明](../testing/gdunit-source-packages.md)及仓库配置为准；来源、发布、固定包验收和历史完整门见[固定包来源与验收年表](../archive/m2/gdunit-source-acceptance-history.md)。Windows 输出捕获、焦点观测、跨盘 Prepare 和历史 CI 的具体失败只在历史记录中按明确症状触发查阅；历史一次通过不证明根因已消除，也不授权重跑。

完整门仍由共享入口负责；本页不创建第二诊断框架，不把 headless、GPU、人工桌面、远端 CI 或成本报告相互替代。任务状态、Issue 评论和远端 CI 是动态事实，不能从历史标题或旧计划页推断。
