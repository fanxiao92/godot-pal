# 多票长任务的信息分工

在规划多票规格、设计多代理交接或排查长会话上下文膨胀时使用。来自 [#31 复盘](../archive/engineering/spec31-retrospective.md) 的建议工作方式，不是新的任务系统、harness 功能或自动授权；现有 Issue、子代理工具、证据目录和项目门禁继续有效。

## 协调者的工作集

Main agent 负责目标与不可变约束、授权范围、依赖图与负责人、当前接口决定、验收索引和下一动作。实现细节、局部诊断、完整日志及逐次 RED/GREEN 留在任务上下文与原始产物中。

| 角色 | 承担的工作 | 返回给协调者 |
|---|---|---|
| Main | 分解、派发、处理跨票冲突、决策升级、集成和交付 | 当前状态与下一动作；不是每个子任务的完整过程 |
| 实施者 | 单一任务的探索、实现、测试及局部故障定位 | 冻结 source 身份、结果、产物引用、未解决项 |
| 独立评审者 | 对冻结 diff 按 Standards/Spec 审查 | finding、证据、影响和复验要求；不以旧报告代替当前版本 |
| 已有检查工具 | 核验数字退出、产物完整性和约定身份 | 结构化结果与原件引用；不要求 LLM 从输出文本猜退出码 |

只有当前请求授权委派时才使用子代理。单任务可直接执行；本分工不强制增加代理层数，也不削弱唯一写入者、实际引擎全局串行或独立验收要求。

## 当前状态与历史分开

复用现有执行记录和任务工具，保留一个权威当前状态；历史事件追加保存，原件不覆盖。压缩或阶段交接携带的是**当前状态和索引**，不是不断继承全部历史摘要。

当前状态至少包含：

- 目标范围及必须保留的约束、已授权/待授权动作。
- 各票依赖、状态、唯一写入者/工作区和 source 身份。
- 已确定的跨票接口、尚需决策的问题。
- 已验收的版本/检查类型/收据引用，及未执行或失败项。
- 正在等待的既有任务标识和下一动作；已发生的远端副作用及恢复入口。

建议先以一页可读摘要为目标，使用后再调整；这是工作集设计目标，不是允许丢弃关键事实的硬字符/Token预算。已完成任务退出常驻细节；遇到接口冲突、收据异常、未知失败或验收证据不匹配时，定点读取原件或安排独立调查。

## 结构化交接

下面是**示例数据，不是现有工具的参数协议**。使用工具已有 outputReference、报告和命令账本承载，不要求建立另一套数据库。

```yaml
task: 35
state: ready_for_review
source:
  head: <actual-commit>
  dirty: false
checks:
  result: passed
  receipt: <existing-report-reference>
findings: []
next: independent_review
```

`passed` 必须绑定明确版本及可核验收据，不是执行者自述。原生账本与被测任务账本分别标识；命令计数、控制器退出、任务退出和报告器退出不能混用。dirty 时引用确切差异身份，而非给旧产物套当前 HEAD。

需要决策时返回一个明确问题、可行选项、推荐理由和证据引用。普通可恢复工程错误在授权内定位；项目规定的崩溃、中止、未知退出和人工门禁按原规则升级。正常交接只返回必要结果和引用，评审全文/日志另存，协调者不默认加载全部过程。适用技能要求完整读取评审报告时仍须照做；本建议不以执行者摘要替代独立评审或必读报告。

## 等待、恢复与评审

- 异步任务在既有工具中登记后，按工具的完成通知恢复；预算内观察不另起第二个 watch，也不为制造进度重复读取相同状态。取消、重试或改变运行方式仍遵守原授权和异常规则。
- 若自动续跑不断唤醒等待中的 main，将其记录为 harness 协调问题单独诊断。不得虚构工具支持的 waiting 状态、擅改 Goal 协议、关闭审计或增加额度来规避。
- 写操作与观察分开：响应不明时先核实副作用；已确认合并、发布或取消，不因读者故障重复写入。恢复绑定同一实际 run/attempt/commit。
- 派发前检查 cwd 存在并冻结 base/head/diff；旧会话仍绑定已删 cwd 时，不假定顶层 cwd 参数会搬迁其内部上下文。选择受支持的恢复方式或使用新上下文。
- 每票按要求做双轴审查；修复复审聚焦 finding 与 delta，集成再检查跨票行为。保留撤回勘误，但不要把每个辅助读者扩展成另一套整规格审查。

## 提示词与压缩工具的边界

协调者提示词可以直接约定：维护上述工作集，按已有收据推进；只在需要决策或证据冲突时读细节；委派须有授权；不把历史全文带回主上下文。配套工具需限制默认输出、提供明确收据和可靠完成通知；只有提示词无法修复缺失的等待机制或混乱账本。

上下文压缩（包括 billion-context）是可选增强，不代替职责和状态分工。先观察工作集是否随已完成任务数持续增长，再决定是否试验。试验需另行确认集成方式、恢复与审计兼容性，尤其避免两套子代理实现重叠；不直接改当前安装、代理路由或全局设置。

验证目标：完成第20个任务时，main 仍能只凭当前任务图、接口、授权与验收索引推进，而不是恢复前19个任务的全过程。试验同时检查关键身份/失败记录保留、恢复正确性和实际费用，不只检查压缩率。
