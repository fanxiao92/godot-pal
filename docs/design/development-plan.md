# 开发计划

## 原则:垂直切片优先

整个游戏太大,不可能一次写完。开发顺序遵循**垂直切片优先**:先用很小的范围把"资源转换 → 加载 → 渲染 → 玩法"整条链路打通,证明架构可行,再横向铺开补全部内容。

`pal-extract` 工具也增量做:先只提取垂直切片需要的那点资源,后面再补全所有 MKF 格式。

## 里程碑

### M0 · 项目骨架与工具链

状态：已完成。实施范围见 [M0 计划](../milestones/m0/plan.md)，当前环境与命令见 [根目录 README](../../README.md)。以下保留里程碑目标；实际采用 xUnit + 进程级 smoke test，GdUnit4Net 的接入决策留待 M2 前完成。

- 使用 Godot .NET 建立 C# 桌面游戏项目,确定 Godot/.NET 版本并验证 CLI 构建。
- 确认并配置 GdUnit4Net 及核心层纯 .NET 测试方案。基本 CI(构建 + 测试)。
- 仓库目录结构、README。

### M1 · 场景资源提取
- 核对真实数据与 sdlpal 的 Win95/98 分支,实现 MKF 读取及当前场景需要的解压能力。
- 只提取 1 张地图、瓦片、相关精灵、调色板及场景对象初始数据,产出 PNG + JSON。实施范围见 [M1 计划](../milestones/m1/plan.md)。
- 保留原始 ID、坐标、显隐状态和脚本入口数值;不执行脚本,不将事件文件作为资源包依赖。
- 不包含事件转写、对话、语言包或字库,不以完整脚本资源闭包阻塞静态场景提取。

### M2 · Godot 场景构建与探索
- 资源加载层、表现层最小渲染:只用 M1 产物显示地图与人物,核对瓦片、遮挡和帧动画。
- 场景系统:队伍行走、地图与对象碰撞、相机。
- 按原始初始数据显示场景对象,不执行进入、交互或自动脚本;脚本驱动的 NPC 行为留到 M3。
- **目标:打通“资源转换 → Godot 加载 → 场景显示与行走”,不要求剧情或对话可运行。** 初始场景构建不等于原版某个剧情时刻的完整还原。

### M3 · 事件与对话垂直切片
- 打通最小真实交互的“事件转换 → 触发 → 执行 → 表现 → 返回探索”,遵循 [事件契约](events-schema.md) 与忠实转写决策。
- 实现切片需要的 trigger/auto 语义、入口和状态迁移、条件/跳转、等待及继续;按实际需要注册具名命令,未支持操作保留为 `raw` 并明确拒绝执行。
- 接入对话显示、语言包与所需字库,默认简体中文,按参考保留中英文消息映射及各自显示控制。它们不是 M1/M2 的前置条件。
- 接入进入脚本与交互后的场景更新,补齐真实切片的动态资源依赖。
- **目标:先跑通一个真实事件,不要求一次完成全游戏所有剧情或指令。** 战斗相关事件随 M4 接入,全量内容与指令覆盖后续逐步补齐。

### M4 · 战斗垂直切片
- 事件能触发一场战斗。
- 最小回合制战斗:普通攻击、回合顺序、胜负判定、经验。
- 战斗 UI 最小版。

### M5 · 数据与脚本全量转换
- `pal-extract` 覆盖所有 MKF 格式。
- 完成原版字节码 → 忠实低层 `events.json` 的全量转写、opcode 注册表和反向编译器,对完整脚本 chunk 逐字节往返验证;不恢复结构化控制流。
- 提取全部场景 / 物品 / 法术 / 怪物数据。

### M6 · 系统补全
- 完整战斗:五行相克、法术、战斗道具、敌方 AI、逃跑、奖励结算。
- 菜单系统全套:背包、法术、装备、状态、商店。
- 存档 / 读档(GameState JSON,通过 Godot FileAccess 写入 / 读取 `user://` 本地文件)。

### M7 · 体验补全
- 音频:预转换的音乐 / 音效 / 语音接入。
- 确认目标 Godot 版本支持的视频格式与播放方案,将 AVI 过场离线转换后接入(内置播放方案优先评估 Ogg Theora `.ogv`,不预设 MP4 / WebM 可直接播放)。
- 转场特效、调色板循环动画(水 / 火)。
- 结局流程。

### M8 · 通关验证与打磨
- 从头到尾能通关。
- 对照原版 / sdlpal 校验忠实度(数值、剧情、触发)。
- 打磨手感、性能。

## 第二阶段(本次范围之外)

忠实移植完成后,才考虑扩展能力:手写新内容的结构化事件子集、现代脚本 API、内容编辑器、新场景 / 剧情 / 玩法等。架构已为此留好空间,但不在当前计划内;结构化命令不能提前视为原版转换器或运行时已支持的功能。

## 实现细节备注

- **音频格式转换**:RIX 是 OPL FM 合成格式,ffmpeg 不直接认 —— 中间需要一个 OPL 渲染器先把 RIX 转成 wav,再转 ogg。属实现细节,到 M7 再处理。
- 每个里程碑进入实现前,在 `docs/milestones/<里程碑>/plan.md` 编写实现计划,再编码。任务规格和实施结果记录在 GitHub Issues,检查由测试与 CI 执行;仅对值得长期保留的特殊调查另写记录。
