# 架构设计

## 两阶段:离线转换 + 运行时

整个项目分成**两个独立的部分**,中间隔一道墙。

```
═══ 阶段一 · 离线转换(独立工具,只跑一次)═══

  MKF 文件 ──▶ [pal-extract 工具] ──▶ 现代项目资源
                                     ├ images/*.png      精灵图集
                                     ├ maps/*.json       瓦片地图
                                     ├ data/*.json       物品/法术/怪物/场景表
                                     ├ audio/*.ogg
                                     ├ video/*          Godot 支持的视频格式(待确认)
                                     └ events/*.json     事件 / 编排
   ▲ MKF 在整个项目里只在这里被碰这一次。

══════════════════ 墙 ══════════════════
   游戏从此只认上面这些文件,代码里没有一行认识 MKF。

═══ 阶段二 · 游戏(运行时)═══

  加载图片 / JSON / 音频 / 视频 ──▶ Godot 桌面游戏
```

- **MKF 解析只活在 `pal-extract` 工具里**,它和游戏是两个独立 package。游戏代码里没有一行认识 MKF,完全脱离。
- `pal-extract` 是独立的 C#/.NET 离线命令行工具,产出 `data/extracted/`(现代资源)。当前工具能力与命令见 [根目录 README](../../README.md#构建测试与运行);转换能力从 M1 起增量实现,可按开发需要重复运行。

## 资源 vs 事件:两类东西

转换时要分清两类东西,它们性质不同。

**1. 资源(被动数据)** —— 加载后被使用,不含逻辑:

| 原版 | 转成 |
|---|---|
| RLE 精灵 | PNG 精灵图集 + JSON(帧偏移 / 锚点) |
| 地图瓦片 | JSON tilemap + 瓦片集 PNG |
| 对话 / 文字 | JSON / 纯文本 |
| 数据表(物品 / 法术 / 怪物 / 场景) | JSON |
| RIX 音乐 / 音效 / 语音 | ogg / mp3 |
| AVI 过场 | Godot 支持的视频格式(内置播放方案优先评估 Ogg Theora `.ogv`,最终方案待确认) |
| 调色板 | 多数烤进 PNG;水 / 火的**调色板循环动画**单独留成数据 |

**2. 事件 / 编排(行为)** —— 是逻辑,不是被动数据:

原版字节码脚本负责的"剧情 / 事件层",采用**忠实低层转写的 JSON 事件文件**(`events/*.json`):一条原始指令对应一条具名命令或 `raw`,保留标签、跳转、顺序后继与原始地址。按场景和共享关系组织文件,通过入口定位 NPC 等调用者,不复制共享指令。文件封套、引用与基础命令以 [事件契约](events-schema.md) 为准。

关键区别:图片是被"画出来",事件 JSON 是被"执行"。运行时有一个**事件系统**读这些 JSON 并执行它们 —— 这不是仿真器,而是每个现代引擎都有的东西(类比 RPG Maker 的事件指令、Unity Timeline)。`events/*.json` 是"活的"资源文件:在硬盘上、脱离 MKF、人可读,但被执行。

**原版转换做反汇编,不做结构化反编译**:不恢复 `if`、循环或对话树,避免在忠实移植阶段引入控制流重构。结构化子集留给后续手写新内容,不属于当前原版产物。该取舍见 [ADR-0001](../adr/0001-faithful-event-transcription.md)。未知 opcode 的 `raw` 只保证保存,不代表运行时可执行;运行时不得借助来源数据直接解释原始 opcode。

**忠实度分两部分验证**:保存全局指令数组的全部地址、消息 ID 和操作数,由反向编译器逐字节验证表示与转换保真;事件系统另外测试 trigger/auto 的执行语义、状态迁移、等待与分支。前者不能替代后者。反向编译器和事件执行器目前均未实现,按里程碑增量推进。

## 场景构建与事件的实施边界

原版 `EVENTOBJECT` 是场景对象记录，包含位置、精灵、显隐状态以及脚本入口；读取对象的显示信息不等于执行事件脚本。

M1 提取静态场景资源，M2 在 Godot 构建场景并验证行走、碰撞和相机。两者保留原始入口数值，但不执行进入、交互或自动脚本，也不依赖事件文件、对话、语言包或字库。事件转写和执行从 M3 的真实交互切片开始，随后逐步扩大覆盖，阶段安排以 [总体路线](development-plan.md) 为准。

部分场景状态由脚本初始化或修改，因此原始初始数据的场景构建不代表某个剧情时刻的完整还原；动态行为和资源依赖在接入事件时验证。

## 运行时分层架构

Godot 桌面游戏(阶段二)内部分四层:

```
┌──────────────────────────────────────────────────┐
│ 外壳层 Shell      Godot 主循环 / InputMap / 本地存档 │
│                   音频播放 / 资源加载 / 视频过场      │
├──────────────────────────────────────────────────┤
│ 表现层 Present.   Godot 2D / 320×200 逻辑视口缩放   │
│                   精灵·地图·文字·转场 / 消息框·菜单·战斗UI│
├──────────────── 命令总线 Command Bus ───────────────┤
│ 核心层 Core       游戏状态 GameState                 │
│ (纯逻辑·可测试)   事件系统 · 场景 · 战斗 · 规则       │
├──────────────────────────────────────────────────┤
│ 资源加载层 Assets  ResourceLoader / FileAccess      │
│                   图片 / JSON / 音频 / 视频(不含 MKF)│
└──────────────────────────────────────────────────┘
```

核心原则:

1. **核心层是纯逻辑**,不碰渲染、不碰 MKF。通过「命令总线」与上层通讯 —— 事件系统不直接画对话框,而是发出 `显示对话` / `播放音效` / `进入战斗` 命令,表现层和外壳层消费。这样核心系统可脱离 Godot 场景树,在纯 .NET 环境中单元测试。
2. **所有"内容"都从资源文件来**,核心代码不硬编码任何剧情、地图、数值。
3. **字节码解析只存在于离线工具中**。运行时事件系统执行转换后的 JSON 命令,保留 trigger/auto 的执行差异;通过可暂停的步进处理等待,不把所有脚本统一成每 tick 一条。第二阶段再为手写新内容接入结构化子集或现代脚本能力,不改变原版转写契约。
4. **Godot 平台适配留在外层**:表现层使用 Godot 2D 节点与逻辑视口,输入使用 InputMap;打包资源通过 `res://` 加载,存档通过 FileAccess 写入 `user://`。具体 tick、缩放和视频播放方案仍待设计。

## 核心层:1 个状态 + 4 个系统 + 1 条总线

```
                ┌────────────── GameState ──────────────┐
                │  队伍/角色 · 背包/金钱 · 对象状态与入口  │
                │  当前场景与坐标 · 游戏进度   (可序列化)  │
                └────────────────────────────────────────┘
                      ▲  所有系统读写这里(唯一真相源)
      ┌───────────────┼────────────────┬────────────────┐
 ┌────┴────┐   ┌──────┴──────┐   ┌─────┴─────┐   ┌──────┴──────┐
 │ 场景系统 │   │  事件系统    │   │  战斗系统  │   │ 规则系统     │
 │ 行走碰撞 │   │ (总导演)     │   │ 回合/公式  │   │ 角色/物品/   │
 │ NPC行为  │   │ 对话/编排    │   │  AI/奖励   │   │ 法术·升级·商店│
 │ 触发检测 │   └─────────────┘   └───────────┘   └─────────────┘
 └─────────┘
```

- **GameState** —— 唯一真相源,可序列化。保留对象状态、可变脚本入口、计数器及其他玩法状态,不凭空添加通用 flags 来代替原版进度。存档 = 把它 JSON 化;读档 = 还原它。暂停中的脚本如何恢复在运行时规格中明确,不只保存静态入口。外壳层负责通过 Godot FileAccess 读写 `user://` 本地文件;核心层不承担文件 I/O。
- **事件系统** —— "总导演"。绝大多数玩法流程由它串:玩家在 NPC 前按确认 → 场景系统检测到交互触发 → 交给事件系统 → 执行该 NPC 的 `events.json`(对话 → 选择 → 满足条件就调战斗系统 / 改 GameState 给物品)→ 回到探索。NPC 的"自动行为"(闲逛、待机动画)也是事件的一种,由场景系统按帧驱动。
- **场景系统** —— 当前地图、队伍行走、NPC 行为、瓦片碰撞、相机滚动、触发检测。
- **战斗系统** —— 回合制战斗。回合顺序、伤害公式、五行相克、敌方 AI、经验升级、奖励结算。公式最密集的硬骨头,严格照 sdlpal 的 `fight.c` / `battle.c`。
- **规则系统** —— 角色属性、升级、物品定义与效果、法术、装备、商店。

**顶层模式状态机**:`探索 ⇄ 事件/过场 ⇄ 战斗 ⇄ 菜单`。主循环每帧把输入交给"当前模式",各模式互不干扰。

## 扩展性:怎么兑现"以后好改"

| 想加的东西 | 怎么加 | 动不动引擎 |
|---|---|---|
| 新场景 | 加一个 `map.json` + 一个 `events.json` | 不动 |
| 新物品 / 法术 / 怪物 | 往 `data/*.json` 加一条 | 不动 |
| 新剧情 / 任务 | 写 `events.json` 里的 event-command | 不动 |
| 新玩法机制(如小游戏) | 加一个新系统模块,挂到模式机上 | 只加不改 |

## 技术栈

当前版本及构建、测试命令统一见 [根目录 README](../../README.md#技术栈与开发环境)。

- **语言与引擎**:C# + Godot .NET,目标为跨平台桌面游戏。
- **离线工具**:独立 C#/.NET CLI,不依赖 Godot 或游戏工程。
- **测试**:核心使用纯 .NET xUnit 测试,CLI 使用真实进程测试,Godot 使用启动 smoke test。GdUnit4Net 尚未接入,M2 前需实际验证或明确替代方案。
