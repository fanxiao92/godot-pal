# M1 实现计划：场景资源提取

状态：**M1 已验收通过。#7～#10 的只读检查、Windows 解码、地图/精灵/场景导出及完整资源包已实现，本地验证、独立 Standards/Spec 审查及修复后复核均通过；任务收尾与实际证据见对应 Issue。** 规格及任务见 [Issue #6](https://github.com/fanxiao92/godot-pal/issues/6)。 本计划承接 [总体路线](../../design/development-plan.md)，只交付离线场景资源。M2 负责 Godot 场景构建与探索，M3 再接入事件与对话；任务规格和执行结果使用 GitHub Issues。

## 1. 目标与范围

从 `data/raw/sdlpal/` 提取一张地图、瓦片、调色板、相关人物精灵和场景对象数据，输出到 `data/extracted/`，供 M2 加载。`Pal.Extract` 保持独立 C#/.NET CLI，Godot 运行时不读取 MKF。

原始输入只读，原始数据和生成物均保持 Git 忽略。保留原始 ID、坐标、方向、帧信息、显隐状态与脚本入口数值，不通过修改对象状态或剧情数据制造展示样例。

**本阶段不包含**：事件转写或执行、对话、语言包、字库、剧情触发、NPC 自动行为、战斗、音视频转换。中英文支持的既定方向保留到 M3，不作为场景资源提取的前提。

## 2. 场景对象与事件脚本的边界

原版 `EVENTOBJECT` 记录既包含 NPC、门、箱子等场景对象的摆放和显示信息，也包含 trigger/auto 脚本入口。读取这些记录并导出显示信息，不等于实现事件系统。

- M1 保留对象字段和原始入口数值作为来源数据；不生成指向尚不存在的事件文件的执行引用，不要求入口对应的脚本已转换。
- M2 根据原始初始数据构建场景，处理显示、行走、碰撞和相机；不执行进入、交互或自动脚本。
- 脚本可能改变人物精灵、坐标、显隐或地图。M1 的依赖范围是所选初始场景的静态资源，不追踪完整脚本资源闭包；动态依赖及入口解析在 M3 接入。
- 此阶段验收的是原始初始数据的提取与场景构建，不是某个剧情时刻的完整还原，也不宣称原版开场已经可运行。

## 3. 数据基线与首个场景

当前包的 15 个 MKF 已通过一次性只读外层检查：DWORD 小端偏移表有序、无越界，末尾等于文件长度；空 chunk 合法。六个压缩归档探针和 14 字节对象表记录符合 SDLPal 的 Windows 数据判定条件，这些线索现已由实际 YJ2 解压、GOP/MGO RLE 与调色板/PNG 像素核对补充验证；不构成对所有资源格式的兼容承诺。

`Sss.mkf` 的 SHA-256 为 `942cb898f14d609475e3bcef0944e4d082ca88f76f4a7171028b451584a5e2ff`。正式工具应记录实际消费文件的散列，不把该散列作为只允许某一份游戏数据的白名单。Windows 格式特征不能证明此重打包数据与未修改的 98 柔情版逐字节一致。

首轮使用以下静态资源切片：

| 输入 | 已核对信息 |
|---|---|
| 地图 ID 12 | `Map.mkf` chunk 12 为 4,236 字节，头部声明解压后 65,536 字节 |
| 地图 12 的瓦片 | `Gop.mkf` chunk 12 为 68,588 字节，按帧读取，不误做 YJ2 |
| 场景 ID 2 | 引用地图 12，初始关联场景对象 ID 1～32；进入脚本地址 `0x0DD9` 仅保留、不执行 |
| 初始对象的非零 MGO 引用 | `21, 29, 30, 55, 57, 207, 210, 211, 239, 398, 628` |
| 主角默认精灵 | 默认角色数据引用 MGO ID 2 |

调色板与昼夜选择应作为可追溯的转换参数记录，按原始数据和参考调用链核对，不凭场景编号猜测。对象无精灵或隐藏时保留该状态，不强制显示。场景名称尚未核实，使用原始 ID，不自行命名。

文字文件、SLF、字库和脚本 chunk 的语义不属于本轮消费范围；它们的存在或缺失不阻塞静态场景提取。

### 输入与错误处理

- CLI 显式接收输入目录，不依赖当前工作目录，不扫描或启动包内 SDLPal 程序。
- 兼容输入文件的大小写差异；同一逻辑名称有多个候选时报告歧义。
- 校验偏移表长度、对齐、顺序和文件范围，截断和越界需定位归档与 chunk。
- 根据归档用途和版本特征决定压缩处理，不把“没有 YJ1 头”当成所有 chunk 都是 YJ2 的证明。
- 沿用帮助返回 0、参数错误返回 2 的已验收行为；检查命令的输入/归档错误返回 1，错误不输出部分成功报告，具体契约见 #7。
- 初次导出写到新的输出目录，明确覆盖策略；不能默认清空已有目录或写回输入目录。

### 解码与产物

- 先支持当前 Windows 场景实际需要的 YJ2，不预先实现完整 DOS/YJ1 支持。
- 解压检查源位流边界、输出上限、回溯距离、终止条件和实际输出长度；不照搬参考 C 中缺少边界检查的内存访问。
- 地图 DWORD、两层瓦片、遮挡高度与碰撞按 `map.c` 核对，不只导出丢失结构的背景图。
- GOP 读取帧与 RLE；MGO 先按 Windows 分支解压，再读取帧与 RLE。保留帧尺寸、透明区域、索引和定位信息。
- 调色板按 `palette.c` 转换；保留后续渲染需要的索引及调色板信息，不只烘焙 PNG 后丢弃来源。调色板动画本轮不执行。
- 输出清单记录版本、输入身份、转换参数及静态资源依赖，资源引用须完整；脚本入口是未执行的来源数值，不按事件执行引用校验。

## 5. 测试与验收

### 自动化

- 沿用真实 CLI 进程入口，断言退出码、stdout/stderr 和输出文件内容；内部算法可补聚焦测试，不能替代命令级验证。
- 人工构造合法/损坏 MKF、最小 YJ2、帧/RLE 和场景记录，覆盖空槽、截断、越界、错误解压长度、非法回溯、透明跳段、无精灵及隐藏对象。
- 以独立期望值核对解压字节、像素和地图/对象字段；同一实现生成期望再检查自己不算保真验证。
- 输入只有场景所需归档、没有消息文件或 SLF 时，完整静态场景转换仍成功；脚本入口非零不要求提供事件文件。
- 同一输入及参数重复转换的内容一致，输入散列不变，输出不泄漏原始绝对目录或无关本机信息。
- 执行 solution 构建与测试；提取工具不引入 Godot 依赖，M0 启动检查继续保留。常规 CI 使用人工构造的小型输入，不分发原版数据。

### 真实数据本地验收

1. 用正式 CLI 复核输入结构及身份，取代一次性探针。
2. 实际解压地图 12，核对长度、地图字段与瓦片引用，导出预览并人工检查颜色、透明、拼接及上下层关系。
3. 核对场景 2 的初始对象数量、ID、坐标、显隐状态、精灵帧及原始脚本入口；不运行进入脚本。
4. 验证整个静态场景资源包的引用和重复输出一致性，确认输入散列未变，原始数据和产物未进入 Git。

M1 完成需要上述自动化与真实数据验收有实际证据。离线检查和预览不能替代 M2 的 Godot 显示、行走与碰撞验证。事件转换、对话、语言包及字库交由 M3；全量脚本转换、反向编译器和逐字节往返交由 M5，具体阶段定义以 [总体路线](../../design/development-plan.md) 为准。
